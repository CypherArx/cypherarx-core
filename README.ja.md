# CypherArx Core

[English version / 英語版はこちら](README.md)

`cypherarx-core` は **CypherArx** の C++ コアです。CypherArx は、主流のパスワードマネージャーでは
表現できない *複雑な* 認証情報（階層構造のエントリ、自由フィールド、複数名義のアカウント）を扱う、
オープンソース・完全ローカル・ネイティブのパスワードマネージャーです。

> **状態: プレアルファ、一般利用不可。** 開発中はリポジトリを非公開にしています。
> オープンソースライセンスは最初の公開時に決めます。

## 範囲

これは **UI を持たない** コアです: 暗号、KEK/DEK の鍵階層、暗号化 SQLite ストレージ、
エントリ／フィールドのロジック、パスワード生成、TOTP、CSV のインポート。**ライブラリ API のみ**を
公開し、**CLI はありません**（設計上の判断）。**UI もありません**（Dear ImGui の GUI は別リポジトリ
`cypherarx-gui` にあります）。

金庫のパスは `std::filesystem::path` で受け取り、SQLite 向けの UTF-8 変換はコア側で行うため、
非 ASCII のパスもどのプラットフォームでも動作します。

金庫の設定（`cypherarx/settings.hpp`、`Vault::settings` と `Vault::set_settings`）は、1 つの
金庫に属し、解錠した後にだけ読めればよい値です。アクセス記録の保持日数、セッションの長さ、
無操作でのロックなどが入ります。コアは値を保存するだけで、それに従って動くのは
アプリケーション側です。値は `settings` テーブルの 1 行ずつで、DEK で暗号化し、キーに
結び付けてあるので、ある値を別のキーへ移すことはできません。書き込みは全キーを保存する
ので、どれを変えたかはテーブルから分かりません。保存されていないキーは既定の値として
読み、この版が知らないキーには触れず、復号や解釈ができない値は既定の値で置き換えずに
`Corrupt` として報告します。金庫を開く前に分かっている必要があるものは、ここには
置きません。それはアプリケーション自身の設定ファイルの役目です。

アクセス記録（`cypherarx/access_log.hpp`、`Vault::record_access`・`access_records`・
`purge_access_records`）は、エントリを見たこと、値をコピーしたことを記録します。「最近
使った」の一覧と、使用回数の順位付けのためのものです。記録はエントリの uuid・操作・時刻で、
まとめて 1 つの値として暗号化するので、ファイルから分かるのは記録の件数だけです。各記録は
その行だけの乱数の id に結び付けてあるので、ある記録を別の記録の上に写すことはできません。
コアは時計を読みません。どの呼び出しも、現在時刻を Unix 秒で受け取ります。記録が有効な
期間は設定の `log_retention_days` が決めます。それより古い記録は返さず、
`purge_access_records` が削除します。0 のときは何も記録しません。読み出しと削除は全記録を
復号します（保持期間があるので件数は小さく保たれます）。復号や解釈ができない記録は
`Corrupt` とし、削除は何も消さずに止まります。

鍵のローテーション（`Vault::rotate_key`）は DEK を取り替えます。マスターパスワードを
受け取ります。新しい DEK は KEK で包む必要があり、KEK は解錠の後は保持していないため
です。データベースの 1 つのトランザクションの中で、新しい DEK を作り、暗号化された値を
すべて古い DEK で復号して新しい DEK で暗号化し（削除済みの行も含みます）、新しく包んだ
DEK を新しいソルトとともに保存します。そのあとメモリ上の DEK を新しいものに替えます。
途中のどこで失敗しても、パスワードが違っても、復号できない値があっても、金庫は元の
ままです。新旧の鍵がファイルの中で併存することはないので、鍵のテーブルも、行ごとの鍵の
番号を追う処理もありません。設計文書（§6.2、§6.3）の、段階的で再開できるローテーション
より単純ですが、あちらが目指した保証はトランザクションがすでに与えています。暗号化
された列は `src/vault.cpp` の `kEncryptedColumns` の 1 か所に並べてあります。暗号化する
列を足したら、そこにも足す必要があります。`tests/test_rotation.cpp` は、名前が `_enc` で
終わる列のうち、ローテーションで変わらなかったもの、またはテストにデータが無いものが
あると失敗します。

確定のあと、ファイルを書き直します（`secure_delete` と `VACUUM`）。古い暗号文と、古い
包まれた DEK を、ファイルに残さないためです。この段階が失敗したときは、ローテーション
自体は済んでいて、呼び出しは `ScrubFailed` を返します。コアの手が届かないのは、ファイルの
外です。SQLite が削除するロールバックジャーナルと一時ファイル、以前の写しやバックアップ、
ファイルシステムや SSD がまだ再利用していないブロックがこれに当たります。ローテーションが
防ぐのは DEK の漏洩です。マスターパスワードの漏洩には、これだけでは効きません（新しい
DEK も同じパスワードで包まれるため）。

マスターパスワードの変更（`Vault::change_master_password`）は、新しいパスワードと新しい
KDF のパラメータで行う、同じ操作です。古いパスワードを検証し、DEK を取り替え、すべての
値を暗号化し直し、ファイルを書き直します。トランザクションも、失敗したときの挙動も、
ローテーションと同じです。DEK を残したままパスワードだけを変える方法はありません。DEK が
残ると、古いパスワードと古いファイルの写しを持つ相手は、その写しから DEK を取り出し、
以後のどの写しもそれで読めてしまいます。パスワードを変えるのは、たいていこの場合の
ためです。これは設計文書（§7.4）とは違います。設計文書は、値を暗号化し直さずに済む
ように、同じ DEK を包み直します。古い写しそのものは、古いパスワードで読めるままです。
これは何をしても変えられません。

インポート（`cypherarx/import.hpp`、`Vault::import_logins`）は、ブラウザやパスワード
マネージャーが書き出す CSV ファイルを読みます。`parse_logins_csv` は呼び出し側のバッファを
その場で書き換えながら読み、バッファの中を指すビューを返します。呼び出し側はファイルを
保護メモリに置いたまま扱い、最後に 1 回消せば済みます。製品ごとの形式は知りません。列を
見出しの名前で探します（順序と大文字小文字は問いません。`name`/`title`、
`url`/`uri`/`login_uri`/`website`、`username`/`login_username`/`login`、ユーザー名が無いときの
`email`、`password`/`login_password`、`totp`/`login_totp`/`otpauth`/`otpsecret`/`otpurl`、
`note`/`notes`/`extra`/`comments`）。パスワードの列も TOTP の列も無いファイルは拒否します。
引用符で囲んだ値、二重の引用符、値の中の改行、CRLF、バイト順マークを扱えます。
**テストは、それらの書き出しに似せた見出しで行っており、製品が実際に書き出した
ファイルでは行っていません。** KeePass の XML と 1Password の 1PUX は読めません。

`import_logins` は、行を 1 つのトランザクションで、service と account として保存します。

service は、名前と、いくつでも持てる URL と、ログイン URL を持ちます。この 3 つは別のもの
です。名前は表示用で、空でもかまいません。URL は、service に付けた種類 `url` のフィールド
です（`kUrlFieldType`。`Vault::urls` で読めます）。URL を 1 つも持たない service もあり得ます
（サイトの無いもの、サイトの分からないアプリ）。ログイン URL は service 自身の `login_url` です。
ログインする場所は service のもので、account ごとのものではないためです。

行はサイトごとにまとめます。サイトは行の URL のホスト（大文字小文字を区別せずに比べます）で、
URL が無ければ名前です。金庫にすでにある service のうち、そのホストを URL のフィールドか
`url` のどれかに持つもの、または URL を持たずその名前のものがあれば、行はそこへ入ります。
無ければ service を作り、行の URL のスキームとホストを URL のフィールドに、行の URL を
ログイン URL に、行の名前を名前にします（名前がホストそのものなら、名前は付けません）。
ホストは書かれたとおりに比べるので、`www.example.com` と `example.com` はまだ別のサイトです。
どのホストが同じ登録ドメインかを見分けるには、公開サフィックスの一覧が要ります。

行ごとに、その service の下に account を 1 つ作ります。account の名前はユーザー名で、メモを
notes に入れます。`ImportOptions::persona_id` を指定すると、その名義を付けます（persona の
エントリでなければ、何も取り込みません）。account が自分のログイン URL を持つのは、行の URL が
service のものと違うときだけです。フィールドには、ユーザー名そのもの（メールアドレスの形なら
Email、そうでなければ ID という名前を付けます。見るのは形だけで、どちらでも値は保たれます）、
パスワード、TOTP のシークレット（`otpauth://` の URL からは取り出します）を入れます。
ユーザー名を account の名前だけでなくフィールドにもするのは、アカウントが対等な識別子
（メールアドレス、電話番号、ハンドル）をいくつでも持ち、書き出しにはそのうち 1 つしか
入っておらず、コピーしたり足したりできるのがフィールドだからです。

保存するものが無い行は飛ばします。サイトとユーザー名がすでにある行も飛ばすので、同じ
ファイルを 2 回取り込んでも何も増えません。そのため、2 回目のファイルでパスワードが
変わっていても、取り込みません。金庫にすでにあるエントリは、決して変えません。
結果として、追加した件数と飛ばした件数を返します。

`erase_file`（`cypherarx/erase.hpp`）は、取り込みの済んだ書き出しファイルのための操作
です。ファイル全体にゼロを書き、それをディスクまで書き出してから、ファイルを削除します。
`overwrite_file` は前半だけを行います。受け付けるのは通常のファイルだけで、ディレクトリ、
シンボリックリンク、存在しないパスは `NotAFile` になり、何にも触りません。上書きが届くのは、
ファイルがいま占めているブロックです（ファイルシステムがその場に書く範囲で）。コアから
見えないものには届きません。SSD や、書き込み時に複製するファイルシステムが割り当て直した
ブロック、以前の写し、バックアップ、クラウドの同期、ブラウザのダウンロード履歴、以前に手で
削除したファイルのごみ箱の中の写しがこれに当たります。

`Vault::merge_service(source, target)` は、2 つの service を 1 つにします（1 つの
トランザクションで行います）。同じものだと分かった service（手で作ったものと、取り込んだ
もの）のための操作です。target は名前とカテゴリを保ちます。source の account は target の
下へ移り、source の URL のフィールドは、target が同じ URL（大文字小文字を区別せずに比べます）を
すでに持っていなければ target へ移り、source は削除されます。target がログイン URL を
持っていなければ、source のものを受け継ぎます。自分のログイン URL を持たず service のものを
使っていた account は、使っていた URL を保ちます。target のログイン URL が別のものなら、
source のものを account に書きます。

`Vault::set_accounts_persona(ids, persona)` は、複数の account に 1 つの名義を付けます
（名義なしにもできます）。1 つのトランザクションで行い、id がすべて account で、名義が
persona のエントリでなければ、何も変えません。

## 技術

- **C++23**、libsodium（XChaCha20-Poly1305 / Argon2id）、SQLite3
- CMake ＋ vcpkg（マニフェストモード）、Ninja
- GoogleTest、CI で AddressSanitizer / UBSan
- エラーモデル: `std::expected` / 結果型。例外は本当に例外的な場合のみ

## ビルド

C++23 コンパイラ、CMake 3.21 以上、Ninja、vcpkg（`VCPKG_ROOT` 設定済み）が必要です。

```sh
cmake --preset default
cmake --build --preset default
ctest --preset default
```

Windows では Visual Studio の開発者シェルから構成する（MSVC の `cl` が `PATH` にある状態）か、
フォルダを Qt Creator / Visual Studio で開いてください（どちらも `CMakePresets.json` を読みます）。
